Implementation architecture · tailmixd

Many tailnets.
One host network.

tailmix runs an independent Tailscale node for every profile, then joins their packet paths behind one host TUN. Stable local addresses remove cross-tailnet IP collisions; translation restores each tailnet’s canonical identity before traffic reaches Tailscale.

one daemon one shared TUN one tsnet.Server / profile Darwin + Linux IPv4 + IPv6 peers

01 · Overview

A host-wide multiplexer around isolated Tailscale engines

There is no active-tailnet switch. The OS sees a single ordinary interface and a collision-free set of effective peer addresses. tailmix selects a profile for every packet; upstream Tailscale continues to own authentication, netmaps, WireGuard, DERP, ACL-visible identity, and transport behavior.

host packet path profile / tailnet boundary DNS path outside tailmixd

Invariant A

One engine, one identity

Every profile has its own machine keys, node keys, login session, netmap, preferences, and local state directory.

Invariant B

No canonical host routes

The OS routes effective addresses only. Canonical CGNAT and ULA addresses are introduced after profile selection.

Invariant C

DNS returns effective IPs

MagicDNS FQDNs never expose a peer’s canonical address to local applications.

02 · Ownership boundaries

tailmix chooses the path; Tailscale secures it

The design depends on the upstream tsnet.Server.Tun hook. tailmix substitutes a channel-backed TUN for each server, but otherwise uses the published Tailscale modules directly.

Security property: an effective address selects a route; it does not become a Tailscale identity. Remote policy sees the selected profile’s canonical identity exactly as it would for an ordinary Tailscale node.

03 · Address model

Three address roles, deliberately separated

Cross-tailnet canonical addresses can collide. tailmix therefore leases a unique effective address to every visible (profile, node, canonical IP) tuple and reserves one host NAT address per active family.

Effective peer IP Host DNS, routes, sockets, shared TUN Collision-free local dial target and profile lookup key Persisted; retained when a peer disappears
Host NAT IP Host interface and host side of packet translation One stable local source/destination per address family Persisted with the selected pool
Canonical Tailscale IP Inside exactly one profile engine and its tailnet Real Tailscale self/peer addressing and ACL-visible traffic Assigned by that tailnet
100.100.100.100 Host DNS configuration and shared TUN Tailscale-defined MagicDNS service address Fixed; never allocated from the effective pool

04 · Data plane

Packet routing and bidirectional NAT

Routing decisions use immutable BART tables. Current peer entries are exact /32 or /128 prefixes; longest-prefix lookup leaves room for future route types without changing the hot path.

Outbound · host → tailnet

  1. The OS sends a packet for an effective peer IP through the shared TUN.
  2. The mux first offers packets for 100.100.100.100 to the local DNS service.
  3. The destination BART table returns the profile and canonical peer IP.
  4. A (profile, address family) source entry returns the canonical self IP.
  5. The mapper rewrites source and destination in place and updates checksums.
  6. The packet crosses the selected ChanTUN into that tsnet.Server.
  7. Tailscale encrypts and sends it directly or through DERP.

Inbound · tailnet → host

  1. A profile engine decrypts a canonical packet and writes it to its ChanTUN.
  2. The mux already knows the profile from the channel that produced the packet.
  3. That profile’s inbound BART table maps canonical peer source to effective source.
  4. The mapper rewrites the canonical self destination to the host NAT address.
  5. Checksums are updated and the packet is written to the shared host TUN.
  6. The OS delivers it to a local socket; normal host firewall behavior applies.
Why both SNAT and DNAT? Source selection is not left to the OS. The host owns one NAT address per family, while each profile has a different canonical self address. Explicit translation makes profile selection deterministic in both directions.

05 · MagicDNS

One service IP, several explicit DNS zones

tailmix reuses Tailscale’s DNS manager, resolver configuration, and OS integration. It supplies an aggregate host table whose answers are effective addresses, then terminates DNS packets inside the TUN with a small gVisor TCP/IP stack.

Routing

Suffixes are explicit

Every active profile contributes its MagicDNS suffix. Search domains are intentionally omitted, so local applications use fully qualified names.

Sharing

Off-suffix FQDNs survive

A shared-in peer can retain a source-tailnet FQDN. tailmix installs an exact-name DNS route without claiming that peer’s entire source suffix.

Self records

The host resolves locally

Each profile’s own MagicDNS name maps to the shared host NAT address; remote peer names map to their effective leases.

Platform integration

On macOS, tailmix asks the Tailscale manager for native split-DNS configuration, producing selective resolver entries rather than blending the machine’s base resolvers into quad-100. On Linux, the upstream configurator selects the available systemd-resolved, NetworkManager, resolvconf, or direct resolv.conf integration. DNS is registered as IPv4-only at 100.100.100.100; returned host records may contain either effective IPv4 or IPv6 addresses.

06 · Packet ownership

Translate in place; copy only when ownership changes

Packet mapping is a hot-path operation. The mapper decodes and rewrites the supplied slice directly; it does not clone packets before SNAT or DNAT.

BoundaryCopy?Reason
packetmap.Outbound / Inboundin placeThe forwarding worker exclusively owns the current packet while translating it.
Host-read buffer → profile Outbound queuecopyThe host TUN read loop immediately reuses its batch buffers while the profile consumes asynchronously.
Profile tun.Device.Write → Inbound queuecopyThe WireGuard/TUN caller retains and may reuse its write buffer after the method returns.
Queue → host TUN writeframing copyThe TUN API requires transport-header headroom before the IP packet.
DNS packet → gVisorcopyThe packet becomes owned by an asynchronous local network stack.
Do not remove an ownership copy without changing the queueing model. Channel-backed TUNs are asynchronous. Passing a reused producer buffer through them would create corruption and data races, even though the mapper itself is safe to operate in place.

07 · Control plane

Every netmap change rebuilds one coherent plan

Each profile watches its local IPN bus for initial state, self changes, peer changes, peer patches, removals, and transitions to Running. Notifications are coalesced; a notification causes a fresh aggregate status read across every profile.

  1. Observe: a profile’s IPN watcher reports a relevant change.
  2. Snapshot: the manager fetches current self IPs, peers, DNS names, suffixes, and shields-up state for all profiles.
  3. Allocate: active nodes reuse or receive effective leases; historical leases remain persisted.
  4. Compile: tailmix builds destination/source BART tables, host addresses/routes, MagicDNS domains, and host records.
  5. Apply host config: addresses and exact peer routes are reconciled on the shared TUN.
  6. Publish data plane: an atomic pointer swap exposes the new immutable packet mapper to subsequent packets.
  7. Publish DNS: the Tailscale DNS manager receives the new aggregate configuration.
  8. Persist: profiles, learned suffixes, NAT addresses, and leases are atomically saved to daemon state.

Concurrency

Readers never lock the route table

The mux holds an atomic.Pointer to an immutable mapper. Packets already in flight finish against the previous plan; later packets see the replacement.

Failure model

Reconciliation is fail-fast

A startup, watcher, aggregate status, route, DNS, or state-save error currently terminates TUN mode. The apply sequence is ordered but not transactional across the OS, mapper, DNS, and disk.

08 · Identity & persistence

Shared process, independent devices

The physical host appears as a separate Tailscale device in every tailnet. Profiles share tailmix’s host network but do not share their Tailscale identity or authentication material.

Daemon state

state.json

Stores pool selection, host NAT addresses, profile metadata, effective leases, and the reserved exit-node shape. It is written as mode 0600 via temporary file + rename.

Profile state

profiles/<id>

Each tsnet.Server owns a separate directory containing its machine identity, node identity, login session, and control-plane cache.

Authentication

Interactive or keyed

Without an auth key, each profile can emit its own interactive login URL. Unattended enrollment uses distinct auth-key-env variables.

tailmix rejects a global TS_AUTHKEY or TS_AUTH_KEY when any profile lacks an explicit per-profile key environment. This prevents one ambient key from accidentally enrolling every identity into the same tailnet.

Networking modes

Default · -mode tun

System-wide IP connectivity

Provides the architecture described in this document: host routes, IPv4/IPv6 translation, inbound delivery, dynamic netmap reconciliation, and MagicDNS through the shared TUN.

Fallback · -mode socks

Userspace TCP milestone

Exposes one SOCKS5 listener and selects a profile by MagicDNS suffix or effective IP before calling tsnet.Dial. It supports TCP only and builds its routing view at startup.

11 · Current scope

Implemented contracts and deliberate limits

Implemented

  • Concurrent direct-node reachability across multiple profiles
  • Stable effective IPv4 and IPv6 leases
  • Shared host SNAT/DNAT with explicit profile routing
  • Dynamic peer, route, mapping, and DNS reconciliation
  • MagicDNS FQDNs, including exact routes for shared-in names
  • Interactive and per-profile auth-key login
  • Darwin and Linux host TUN implementations

Not currently implemented

  • Advertised subnet routes, app connectors, or route remapping
  • Exit-node/default-route application or cross-profile failover
  • Short-name resolution or tailnet search domains
  • Automatic cross-tailnet forwarding or anti-bridging firewall rules
  • Per-profile failure isolation in the daemon reconciliation loop
  • A complete operational control/status CLI
